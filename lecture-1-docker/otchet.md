Capabilities и seccomp ограничивают процесс на разных уровнях. Перавй дает привелегии  процессу, например после удаления CAP_SYS_TIME процесс теряет право изменять системное время. Seccomp ограничивает набор системных вызовов, которые процесс может выполнять, при попытке получает SIGSYS и завершается.

## Часть 5 — свой Docker одной командой
Собрал все команды из частей 2–4 в один скрипт mydocker.sh, который поднимает api одной командой. Скрипт делает то же самое, что мы делали вручную: unshare создаёт namespaces (pid, mount, net, uts, ipc, user), затем создаётся cgroup v2 с лимитами из части 3 (memory.max = 30 МБ, cpu.max = 0.5 ядра, pids.max = 20), процесс кладётся в эту группу, дальше через capsh дропается CAP_SYS_TIME и поверх навешивается seccomp-фильтр на смену времени. После запуска скрипт сам дёргает /health изнутри сетевого namespace и получает ok — сервис поднялся изолированным, с лимитами и урезанными правами.

Дальше запустил тот же сервис через docker run с теми же ограничениями (--memory=30m, --cpus=0.5, --pids-limit=20, --cap-drop=SYS_TIME, --security-opt seccomp=seccomp.json) и сравнил со своим скриптом.

Что совпало: изоляция и лимиты работают одинаково. api внутри становится PID 1 со своим hostname и своей сетью, /eat ловит OOM на 30 МБ, /burn троттлится на половине ядра, fork-бомба упирается в 20 pids, а смена времени отбивается и дропнутой привилегией, и seccomp'ом (SIGSYS).

Чего не хватает скрипту (и что Docker делает сверху):
- Сеть. У скрипта namespace пустой, поэтому /health доступен только изнутри. Docker сам поднимает veth-пару с bridge и NAT и пробрасывает порт (-p 8080:8080), так что сервис виден с хоста. Это главное отличие.
- Готовая файловая система. Скрипт запускает бинарь прямо с хостового /, то есть процесс видит весь хост. Docker делает pivot_root в распакованный из слоёв overlayfs, и контейнер видит только свой rootfs (это уже часть 6).
- Жизненный цикл: рестарты, docker logs, docker stop/exec, tini для reaping зомби через --init. У скрипта только wait и ручная чистка cgroup по trap.
- Полноценный seccomp: у меня в профиле заблокированы 4 вызова для демонстрации, дефолтный профиль Docker запрещает несколько десятков опасных syscall'ов и по умолчанию дропает почти все capability, а не одну.

Что скрипт делает, а Docker по умолчанию нет: у меня всегда включён user namespace (--map-root-user), то есть root внутри — это непривилегированный uid снаружи. У Docker userns-remap по умолчанию выключен, и root в контейнере совпадает с реальным root на хосте.

Вывод: docker run, containerd и runc не изобретают изоляцию — они настраивают те же самые механизмы ядра (namespaces, cgroups, capabilities, seccomp), которые мы собрали руками в mydocker.sh, только аккуратно, в правильном порядке и с готовым образом и сетью в придачу.
